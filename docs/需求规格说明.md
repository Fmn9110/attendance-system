你是一名资深全栈开发工程师，请帮我从零开发一个【线上班级点名管理系统】。

这个系统最终需要部署到我自己的服务器，服务器环境为：

* Ubuntu 22.04 LTS 64位
* 前端：原生 HTML + CSS + JavaScript
* 后端：Python
* 数据库：优先使用 SQLite，项目结构设计时保留后续切换 MySQL/PostgreSQL 的能力
* 后端推荐使用 FastAPI
* 前后端通过 REST API 通信
* 最终通过 Nginx + Uvicorn/Systemd 部署
* 系统主要面向手机浏览器使用，因此必须优先进行移动端 UI/UX 设计，同时兼容电脑浏览器
* 不使用 React、Vue 等大型前端框架
* 页面尽量简洁、清晰、操作快速，不要做复杂的后台管理风格

项目定位：

这是一个供 5 个班级长期使用的手机端点名系统。

每个班级有独立密码，班长进入对应班级后，可以上传本班学生 Excel 花名册，然后直接进行点名。

核心目标是：

【打开班级 → 输入密码 → 进入点名页面 → 所有学生直接显示在同一个页面 → 逐个设置到课状态 → 完成点名 → 自动保存时间 → 后续可以查询历史 → Excel 导出】

整个操作流程必须非常简单，班长使用手机即可完成。

━━━━━━━━━━━━━━━━━━
一、班级系统
━━━━━━━━━━━━━━━━━━

首页显示 5 个班级。

目前暂定：

* 计科2601班
* 计科2602班
* 计科2603班
* 计科2604班
* 计科2605班

但是代码不要写死成只能支持 5 个班，数据库设计应支持未来增加班级。

首页效果要求：

* 页面简洁
* 显示班级名称
* 每个班级使用独立密码
* 点击班级之后进入该班级登录页面
* 输入正确密码后进入该班级点名系统
* 不同班级的数据完全隔离
* A 班不能查看 B 班的数据
* 班级密码不能以明文直接存储，后端必须进行安全哈希处理
* 登录状态需要保持一段时间，避免班长操作过程中频繁重新输入密码

不要设计复杂的用户注册系统。

目前系统主要采用：

【班级 + 班级密码】

作为基础权限控制即可。

━━━━━━━━━━━━━━━━━━
二、学生花名册 Excel 导入
━━━━━━━━━━━━━━━━━━

每个班进入系统后，需要能够上传本班 Excel 花名册。

Excel 是整个点名系统的基础数据来源。

Excel 至少必须包含：

1. 学号
2. 姓名

电话为可选字段：

3. 电话

也就是说：

【学号 + 姓名】是强制字段

【电话】可以没有。

例如 Excel：

学号 | 姓名 | 电话
20260001 | 张三 | 13800138000
20260002 | 李四 | 13900139000
20260003 | 王五 |

如果 Excel 没有电话列，也必须能够正常导入。

如果存在电话，则在学生信息中显示电话。

导入 Excel 时必须进行数据校验：

* 缺少“学号”列：禁止导入
* 缺少“姓名”列：禁止导入
* 学号为空：标记错误
* 姓名为空：标记错误
* 学号重复：提示
* 空白行自动忽略
* 电话为空允许
* 尽量兼容 Excel 常见格式
* 优先支持 .xlsx
* 有条件的话兼容 .xls

导入后：

* 学生数据保存到数据库
* 不要每次点名都重新读取 Excel
* 后续点名直接使用数据库中的学生列表

需要考虑“重新上传花名册”的情况。

默认设计为：

上传新 Excel → 后端校验 → 页面显示导入结果 → 班长点击“确认导入” → 更新该班当前学生名单。

历史点名记录不能因为重新上传花名册而被删除。

也就是说：

【学生名单】和【历史点名记录】必须分开存储。

━━━━━━━━━━━━━━━━━━
三、最重要的点名页面
━━━━━━━━━━━━━━━━━━

点名页面必须是整个项目最核心的页面。

用户主要通过手机进行操作。

要求：

【学号、姓名、电话、到课状态必须直接显示在同一个页面】

严禁采用：

* 点击学生后弹出 Modal
* 点击学生后二级窗口
* 点击学生后跳转到其他页面
* 使用多层弹窗进行状态选择

所有信息和操作必须在一个点名页面中完成。

页面结构建议：

顶部：

* 班级名称
* 当前日期
* “开始本次点名”按钮
* “结束本次点名”按钮
* 上传/管理花名册
* 历史记录
* 导出

中间：

学生列表。

每个学生显示：

【学号】
【姓名】
【电话（有则显示）】
【当前到课状态】

每个学生后面直接提供状态按钮。

例如：

○ 未点名
[已到]
[迟到]
[病假]
[其他]

状态按钮点击后立即改变当前学生状态。

不要弹窗。

整个页面应该类似移动端任务列表，而不是传统后台管理表格。

━━━━━━━━━━━━━━━━━━
四、到课状态
━━━━━━━━━━━━━━━━━━

每个学生只有以下 4 种正式状态：

1. 已到
2. 迟到
3. 病假
4. 其他

另外在实际操作过程中增加一个：

【未点名】

用于表示当前还没有处理。

因此数据库中的状态建议为：

* pending
* present
* late
* sick_leave
* other

中文显示：

* 未点名
* 已到
* 迟到
* 病假
* 其他

要求：

点击按钮以后立即保存前端状态。

最好采用 AJAX / Fetch API 与后端通信，不要每次点击都刷新整个页面。

━━━━━━━━━━━━━━━━━━
五、“其他”必须在页面内输入
━━━━━━━━━━━━━━━━━━

当班长点击：

【其他】

不要弹出窗口。

必须直接在当前学生这一行展开一个输入区域。

例如：

其他：
[请输入具体情况………………]

填写完成后：

[保存]

示例：

其他：事假

其他：参加比赛

其他：临时离校

其他：家中有事

“其他”必须支持具体文字说明。

如果状态从“其他”切换成其他状态：

* 之前的备注可以自动清空，或者保留在历史记录中
* 当前显示状态必须以最新状态为准

整个过程都不能出现 Modal 弹窗。

━━━━━━━━━━━━━━━━━━
六、点名开始时间
━━━━━━━━━━━━━━━━━━

这是非常重要的业务逻辑。

一次点名 session 必须记录：

1. 点名开始时间
2. 点名结束时间

【点名开始时间】的定义：

不是点击“开始点名”按钮的时间。

而是：

【班长第一次给任意一个学生设置到课状态时的具体时间】

例如：

19:00:01 给第一个学生点“已到”

那么：

本次点名开始时间 = 19:00:01

之后处理其他学生，无论花费几分钟，都属于这一次点名。

━━━━━━━━━━━━━━━━━━
七、点名结束时间
━━━━━━━━━━━━━━━━━━

班长把所有学生处理完以后，点击：

【结束本次点名】

系统记录：

本次点名结束时间

例如：

点名开始：
2026-09-19 19:00:01

点名结束：
2026-09-19 19:07:26

并自动计算：

点名耗时：
00:07:25

建议系统自动判断：

如果仍然存在“未点名”学生：

提醒班长还有多少人没有处理。

但是不要使用弹窗。

可以直接在页面顶部显示：

【还有 3 名学生未完成点名】

同时允许班长选择：

【继续点名】
【仍然结束本次点名】

不要强制阻止结束。

━━━━━━━━━━━━━━━━━━
八、同一天允许多次点名
━━━━━━━━━━━━━━━━━━

这是必须支持的功能。

一个班长一天可能进行多次点名。

例如：

2026-09-19

第一次点名：
08:00 - 08:06

第二次点名：
10:00 - 10:05

第三次点名：
14:00 - 14:07

第四次点名：
19:00 - 19:08

这 4 次点名必须是 4 个独立的点名 Session。

绝不能覆盖之前的数据。

每次点名必须创建新的 session。

因此：

同一天可以无限次点名。

不同日期也可以无限次点名。

历史数据长期保存。

十九、数据保存机制
━━━━━━━━━━━━━━━━━━

非常重要：

不能等到最后点击“结束本次点名”才一次性提交全部学生数据。

因为手机可能：

* 刷新
* 浏览器崩溃
* 网络暂时断开
* 误关闭页面

所以：

每次学生状态发生变化时，都应该通过 API 保存到后端。

前端同时进行本地临时缓存。

建议使用：

localStorage / IndexedDB

保存当前未完成点名 session 的临时状态。

如果页面刷新：

重新打开该班级后，可以恢复当前未完成点名。

二十、网络异常处理
━━━━━━━━━━━━━━━━━━

手机点名非常依赖网络。

所以必须考虑：

网络请求失败时：

页面不能直接丢失用户刚刚选择的状态。
